# Deployment options

All three options use the same dashboard and `COSMO_DATA_MODE` setting:

| Mode | Data source | Storage / collector | GUI |
| --- | --- | --- | --- |
| `realtime` | Fetch latest upstream reports when the dashboard loads or refreshes | No database access, migrations, or scheduled collection | Current watches, locations, latest steps, safe zones, alarms, schedules, and current notification feed. No saved history, activity timeline, historical step charts, or History navigation. |
| `history` (default) | Read collected snapshots | Persistent database; collect every five minutes | Current overview plus saved history, timeline, and historical step charts. |

Realtime means direct reads of the latest reports available from COSMO, not a streaming GPS connection. The page polls every five minutes while visible and supports manual refresh. It does not wake watches. No custom persistence backend is needed in realtime mode; a server component is still needed to protect account credentials and authenticate visitors. Browser-only deployment would expose those credentials.

These files are installation templates. Editing or using them does not modify the existing managed Site. Do not deploy this checkout over an existing Site unless explicitly requested.

## Environment variables

The table covers dashboard runtime settings, container runtime variables, and the hosted collector scheduler. Keep credentials in a private env file, Kubernetes Secret, or Sites hosted secrets.

| Variable | Applies to | Default / requirement | Description |
| --- | --- | --- | --- |
| `COSMO_DATA_MODE` | All deployments | `history`; accepts `history` or `realtime` | Selects saved snapshots with database-backed collection, or direct reads of the latest COSMO reports. Kubernetes overlays explicitly set their chosen mode. |
| `COSMO_EMAIL` | All deployments | Required for upstream reads and collection; required at container startup | COSMO account email used for server-side authentication. Store as a secret. |
| `COSMO_PASSWORD` | All deployments | Required alongside `COSMO_EMAIL` | COSMO account password. Store as a secret; never expose it to the browser. |
| `DASHBOARD_AUTH_ENABLED` | All deployments | `true`; accepts exactly `true` or `false` | Controls application login for dashboard pages and read APIs. Disabling it on Sites still preserves the owner-private platform policy. |
| `DASHBOARD_USERNAME` | Containers | Required when dashboard login is enabled; otherwise omitted | Separate Basic-auth username for visitors. Must contain printable ASCII without spaces or a colon. Do not configure on Sites. |
| `DASHBOARD_PASSWORD` | Containers | Required when dashboard login is enabled; otherwise omitted | Separate Basic-auth password for visitors. Must be nonempty printable ASCII; spaces are allowed. Store as a secret. Do not configure on Sites. |
| `COSMO_COLLECTOR_ENABLED` | Containers | Enabled in `history` unless set to exactly `false` | Controls the bundled scheduler, which collects after startup and every five minutes. Has no effect in `realtime`; disabling it does not disable the collection endpoint. |
| `COSMO_STATE_DIR` | Containers | `/data` | Writable directory for Wrangler's local persistence, including SQLite history. Mount persistent storage here in history mode and keep the mount path aligned if changing it. |
| `SELF_HOSTED` | Container Worker | Startup sets `true` | Selects container authentication instead of Sites authentication. Generated by `deploy/start.mjs`; do not configure on a managed Site. |
| `COSMO_COLLECTOR_TOKEN` | Container Worker with dashboard login disabled | Generated privately at each startup | Internal secret authenticating collection and other protected POST/MCP requests. Startup supplies it to the Worker and bundled scheduler; a user-provided environment value is not used. |
| `NODE_ENV` | Container runtime | Image sets `production` | Runs Node dependencies in production mode. |
| `WRANGLER_SEND_METRICS` | Container runtime | Image sets `false` | Disables Wrangler telemetry. |
| `WRANGLER_WRITE_LOGS` | Container runtime | Image sets `false` | Disables Wrangler log-file writing. |
| `WRANGLER_LOG_PATH` | Container runtime | Startup sets a temporary runtime directory | Keeps any Wrangler log output outside the persisted history volume. Startup overrides an inherited value. |
| `WRANGLER_REGISTRY_PATH` | Container runtime | Startup sets a temporary runtime directory | Location for Wrangler's local development registry. Startup overrides an inherited value. |
| `MINIFLARE_REGISTRY_PATH` | Container runtime | Startup sets a temporary runtime directory | Location for Miniflare's local registry. Startup overrides an inherited value. |
| `CLOUDFLARE_CF_FETCH_ENABLED` | Container runtime | Startup sets `false` | Disables fetching Cloudflare request metadata in the local runtime. Startup overrides an inherited value. |
| `SITE_URL` | Hosted collector CronJob | Required; supplied from Secret key `site-url` | Exact HTTPS Site origin to collect from. Must match `SITE_ORIGIN` (a trailing slash is tolerated here). |
| `SITE_ORIGIN` | Hosted collector CronJob | Script fallback: `https://dashboard.example.com`; configure for deployment | Pins collector requests to the intended HTTPS origin. Must have no path, trailing slash, query, fragment, explicit port, or user information. The CronJob supplies it from the same Secret key as `SITE_URL`. |

Compose forwards only the six variables listed in `deploy/compose.yaml`. To customize `COSMO_COLLECTOR_ENABLED` or `COSMO_STATE_DIR`, add an explicit `environment` mapping in that file or a Compose override; putting them in `--env-file` alone does not pass them into the container. In Kubernetes, configure these optional settings in the Deployment's `env` list.

`DB` is a D1 resource binding, not an environment variable. It is required for history mode and omitted in realtime mode. The hosted scheduler's `service-token` is also not an environment variable: it is read from the mounted Secret file `/var/run/secrets/cosmo/service-token`.

## Optional dashboard login

`DASHBOARD_AUTH_ENABLED=true` is the default. Set it to `false` to open the dashboard pages and read APIs without an application login. COSMO account authentication stays server-side and remains required. Anyone who can reach an installation with login disabled can read its family data; use this setting behind your own access gateway, VPN, or on a trusted private network.

For Compose, put `DASHBOARD_AUTH_ENABLED=false` in the private env file and recreate the container. `DASHBOARD_USERNAME` and `DASHBOARD_PASSWORD` may then be omitted. For Kubernetes, change `DASHBOARD_AUTH_ENABLED` in your overlay's Deployment environment to `"false"`; only COSMO credentials remain required in the Secret. For Sites, configure it as a hosted runtime value in a new installation. It bypasses this application's login checks but **does not bypass Sites' owner-private platform policy**. No existing Site's audience or secrets are changed by the source setting.

In containers, POST/collection/MCP requests still require an internal collector token when visitor login is disabled. Startup generates that token privately for the bundled scheduler; it is never sent to browsers. External collectors must use a separately designed service-authentication integration instead of treating login-disabled mode as an unauthenticated collection endpoint.

## Docker Compose

From `dashboard/`, copy `deploy/.env.example` to a private file outside the repository. Fill in the four credentials. `DASHBOARD_USERNAME` and `DASHBOARD_PASSWORD` are separate browser access credentials, not your COSMO login; use printable ASCII and no colon in the username. Set `COSMO_DATA_MODE=realtime` or `history`.

```sh
docker compose --env-file /private/cosmo.env -f deploy/compose.yaml config --quiet
docker compose --env-file /private/cosmo.env -f deploy/compose.yaml up -d --build
```

Open `http://localhost:8080` and enter the dashboard access credentials. The port binds to loopback. For remote access put a private HTTPS reverse proxy or VPN in front of it; Basic authentication requires transport encryption off-host. Never print expanded Compose configuration because it contains secrets.

The image runs the built Sites Worker using the pinned Wrangler/Miniflare local runtime. This preserves the existing D1 SQL API using **local SQLite**, with no Cloudflare account, remote D1, or Sites dependency. This is a single-instance runtime; Wrangler is a development runtime rather than a horizontally scalable application server. Evaluate that limitation before using it for a production SLA.

History migrations apply automatically at startup and a bundled scheduler calls the local authenticated collector after startup and every five minutes. Set container environment `COSMO_COLLECTOR_ENABLED=false` only when an external scheduler handles collection or for offline startup checks. History lives in the `history` volume at `/data`. Realtime binds no database and starts no collector; the mounted volume remains untouched, so switching modes does not erase existing history. Restart after changing the env file:

```sh
docker compose --env-file /private/cosmo.env -f deploy/compose.yaml up -d --force-recreate
```

Stop with `down` without `-v` to preserve saved history. Back up the whole volume with the container stopped; it can contain SQLite WAL files and private family data. Startup fails on missing access credentials, invalid mode, or failed migrations. `/healthz` checks the runtime only, not COSMO connectivity.

## Kubernetes

Build the same image, tag it for your private registry, and push it. Set the overlay image with Kustomize's `images` configuration or `kubectl set image` after applying. Configure registry pull access if needed. Example build:

```sh
docker build -f deploy/Dockerfile -t registry.example.com/private/cosmo-dashboard:VERSION .
docker push registry.example.com/private/cosmo-dashboard:VERSION
```

In your chosen namespace, provision Secret `cosmo-dashboard-secrets` with `COSMO_EMAIL`, `COSMO_PASSWORD`, `DASHBOARD_USERNAME`, and `DASHBOARD_PASSWORD`. A private env file can be used without putting values in shell arguments:

```sh
kubectl create secret generic cosmo-dashboard-secrets --from-env-file=/private/cosmo-credentials.env
kubectl apply -k deploy/kubernetes/realtime
# OR, for database-backed history:
kubectl apply -k deploy/kubernetes/history
kubectl set image deployment/cosmo-dashboard dashboard=registry.example.com/private/cosmo-dashboard:VERSION
kubectl rollout status deployment/cosmo-dashboard
kubectl port-forward service/cosmo-dashboard 8080:8080
```

Use a credentials-only env file; mode belongs in the overlay. Each overlay supplies its mode. The Service is private `ClusterIP`; no public Ingress is provisioned. Open `http://localhost:8080` through port-forward, or configure your own private HTTPS ingress and network access controls.

The history overlay creates a 2 GiB `ReadWriteOnce` PVC using the cluster's default storage class. Adjust capacity/class for your cluster. It mounts `/data` and uses one replica with `Recreate` updates to avoid concurrent SQLite writers. The realtime overlay uses temporary storage and has no PVC dependency. Do not scale either overlay horizontally. Switching overlays does not delete an existing PVC; switch back to history to mount it again. Stop the Deployment before volume backups. Secret updates require a rollout restart. Review rendered manifests with `kubectl kustomize` before applying.

## Sites (new installation)

See [the copyable installation prompt](../deploy/sites/INSTALL_PROMPT.md). Use a **new owner-private Site** and a separate sanitized checkout. Keep ChatGPT/Sites authentication and hosted runtime secrets. Never use container `SELF_HOSTED` or dashboard Basic-auth credentials on Sites.

For realtime, merge `deploy/sites/hosting.realtime.json` into the new checkout's `.openai/hosting.json`, preserving its newly registered project identity. Set hosted runtime `COSMO_DATA_MODE=realtime`, `COSMO_EMAIL`, and `COSMO_PASSWORD`. Do not provision D1, MCP collection capability, or a collection schedule.

For history, merge `deploy/sites/hosting.history.json` instead, set `COSMO_DATA_MODE=history` (or omit it), and provision D1 binding `DB`. The Sites publishing workflow applies the Drizzle migrations. Configure unattended collection every five minutes using the owner-private collector MCP tool or supported service access. Test collection before considering history installed; the dashboard reads stored snapshots and otherwise starts empty.

Changing modes on a future Site is a runtime setting plus matching storage/capability declarations. Disable its collector schedule when selecting realtime; switching back requires D1 and the schedule. No history is automatically copied from another installation. Use native Sites tools for secrets; never embed credentials, service tokens, Site identity, or private records in the installation prompt.

## Existing collector scheduler template

Provision your own owner-private Site with D1 binding `DB` and MCP capability. `.openai/hosting.json` is a generic source template; add a real project identity only in your private deployment checkout. Set COSMO credentials as server runtime secrets. Publish only after tests, typecheck, and a verified build. Do not broaden access without explicit account-ownership authorization.

`deploy/collector-cronjob.yaml` is a scheduler template. It reads the Site origin and service credential from Secret `cosmo-site-service`, with keys `site-url` and `service-token`. Configure `site-url` as the exact HTTPS origin, without path, query, fragment, port, or user information. The trigger pins requests to that configured origin and refuses redirects. The scheduler context and account URL are deployment choices, not source constants.

Provision the trigger ConfigMap and Secret through private stdin/tooling. Do not store secret values in manifests, commands, ordinary files, or logs. Check sanitized status/counts only.

Local persistence follows the [Cloudflare local D1 contract](https://developers.cloudflare.com/d1/best-practices/local-development/); startup uses [local migrations](https://developers.cloudflare.com/d1/reference/migrations/), never remote database commands.
